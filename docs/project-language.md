# プロジェクトの言語と表記

SpecQR Reader の公開文書、開発記録、GitHub 上の説明は日本語を中心にします。検索と導入の入口として、README 冒頭の短い English summary、正式名称、API 名、ビルドコマンドは維持します。

基本方針は [SpecQR の言語方針（固定コミット）](https://github.com/SpecQR/SpecQR/blob/16efc6c0a8e397c9df3d051d20fce6c1eebdfad7/docs/project-language.md) に従います。空白の細則は、利用者が指定した Ringodesk の規則を優先します。SpecQR 側の助数詞・日付・百分率の例と異なり、本文では `10 件`、`2026 年 10 月 12 日`、`95 %` と書きます。

## 適用範囲と保護する内容

- README、利用・ビルド・API・制限・検証・来歴の説明を日本語中心にします。
- GitHub Actions の表示名・説明、今後の変更記録・コミット・レビュー要約も日本語を基本にします。
- API 識別子、型、オプション、ファイル名、パス、URL、メールアドレス、コマンド、コード、正規表現、版番号、ハッシュ、機械用の数値・日時、QR 出力のバイト列は変更しません。
- MIT ライセンス、第三者ライセンス、直接引用と原文を保存する出典文言は原文のまま保持します。引用内部の表記を本規則へ合わせません。
- 実装の挙動、エラー・警告・診断の文字列、API、配布版番号は翻訳の対象にしません。コード例の内容も保護します。

日本語化は検証範囲の拡張ではありません。実験的な実装であること、未検証の条件、画像探索の不完全性、割り当て失敗の扱いを省略しません。ECI、FNC1、Structured Append のメタデータを保持することと、文字列への変換・GS1 解釈・シンボルの再構成を実行することを区別します。

## 空白

日本語と英単語・算用数字の境界には、通常の半角スペース U+0020 を 1 個入れます。助数詞、日付、金額も対象です。数値と単位の間も空け、百分率は `95 %` とします。全角スペース、改行禁止空白、細い空白で代用せず、空白を重ねません。

```text
API を使う
M1 搭載の Mac
最大 5 時間、第 2 世代、10 件
2026 年 10 月 12 日、10,000 円
32 MiB、250 ms、600 dpi、256 GB、10 Gbps
95 % の結果、25 °C
```

小数点、桁区切り、版番号、時刻・機械用日付の内部を分割しません。単位の大文字・小文字と意味を保ち、GB と Gb、Mbps と MB/s を置き換えません。平面角は `90°`、`30′`、`15″` のように数字へ続けます。温度は `25 °C` とし、`°C` の内部は分割しません。

macOS、M1、USB-C、4K、MacBook Air、iPhone 16e など、正式名称の内部表記は維持します。外側の境界だけを整えます。

句読点や日本語の括弧へ機械的に空白を足しません。たとえば「Mac」、Mac（税込）、API、型のように書きます。日本語本文には原則として「、。」を使い、英語の文や引用は元の句読法を保ちます。

## Markdown と HTML

強調・リンク・HTML タグを挟む場合も、表示結果で同じ空白規則を満たすようにします。リンク先、タグ・属性・構文、インラインコードの内部を変更しません。画像の代替テキストが文章なら同じ規則を使い、装飾画像の空の代替テキストは維持します。

```markdown
**API** を使う
[API](api.md) を確認する
`decode_grid()` を呼び出す
<strong>Mac</strong> の設定
```

直接引用は原文を確認して保持します。自動検査に例外が必要なら、ファイル・行・規則・対象断片・理由を指定した狭い例外として記録します。引用らしい文章を一括で除外したり、ファイル全体を無条件に許可したりしません。

## 正式名称と公開状態

SpecQR Reader、QR Code Model 2、Structured Append、GS1 Digital Link、C++17、CMake、GitHub、GitHub Actions、ZXing Java などは正式な綴りを使います。技術識別子を説明上の都合で翻訳したり、大文字・小文字を変更したりしません。

このプロジェクトは C++ のソースを配布します。SpecQR の npm 固有の用語や仕組みをそのまま持ち込みません。「公開済み」は取得できるリポジトリの正確なコミットを根拠にし、タグ・リリース・バイナリ配布の有無は別々に記録します。CI の設定を追加しただけで実行成功とは記載せず、対象コミットと完了した実行を示します。

## 自動検査と人による確認

表記チェッカーは Python 3.8 以降の標準ライブラリだけを使います。Reader の実行時依存にはなりません。

```sh
python3 tools/verify_writing.py
python3 tests/test_writing.py
make test-writing
```

チェッカーはリポジトリ直下と `docs/` 配下の Markdown、および `.github/workflows/` 配下の対応する表示名・説明・コメントを読み取ります。保護領域を区別し、空白・既知の単位・正式名称など、機械的に判定できる範囲だけを検査します。本文を書き換える機能はありません。`LICENSE` と第三者ライセンスは対象に含めません。

Markdown と YAML の完全な構文解析器ではありません。対応構文と保護領域の範囲はチェッカーの説明とテストで明示し、複雑な構文、原文引用、翻訳の意味、すべての表示上の境界はレビューでも確認します。検査に合格しても、全表記・全翻訳が正しいことの証明にはなりません。

不正例が検出されることと、正しい例・保護領域が変更されないことを対にして検証します。同じ入力を再検査したときの結果とファイルのバイト列も確認し、再適用で空白を増やしません。CI では表記チェックとそのテストを既存のビルド・検証に追加します。
